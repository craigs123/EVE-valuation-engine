The pipeline

Eight stages run between a drawn area and a total. Order is load-bearing — each stage consumes the previous one's output.

01
Sample points are placed inside the polygon
A regular grid is laid over the polygon's bounding box and clipped to the polygon itself with a vectorised point-in-polygon test. If clipping loses too many points, the grid densifies until the target count of interior points is recovered, then deterministically subsamples back down. Points are grid cell centres — there is no randomness, so an analysis is reproducible. Default 10 points, user-configurable to 100.
utils/openlandmap_integration.py:1350 · _generate_sample_points()
02
Each point is assigned a land-cover code
Land cover is queried per point from OpenLandMap via its STAC API, returning an ESA CCI class code. The data source is recorded per point so real satellite reads can be distinguished from fallbacks.
utils/openlandmap_stac_api.py · utils/openlandmap_integration.py
03
Codes are routed to ESVD ecosystem types
A single mapping table translates each CCI code to one ESVD ecosystem type — 10 → Agricultural, 170 → Mangroves, 190 → Urban. Users can override any row in Analysis Settings; overrides are pushed into the live routing table for the session.
utils/esa_landcover_codes.py:179 · DEFAULT_LANDCOVER_MAPPING
04
Water bodies are classified by the user
Code 210 is deliberately treated as unresolved. If any sample point returns 210, the analysis halts and asks the user to classify all water points at once as Ocean (Marine), Rivers/Lakes (Rivers and Lakes), or Coastal. The original code is retained on each point for provenance. Water is valued, not excluded.
app.py:5301–5372
05
Composition becomes area weights
Each ecosystem type's share is its point count over successful queries. That proportion is rounded to one decimal place as a percentage before being used, so the arithmetic matches the percentages shown in the UI. Each type's area is the total hectares times its rounded share.
app.py:5664–5670
06
Forests resolve to a climate subtype
A generic Forest is refined by latitude before coefficient lookup, because boreal, temperate and tropical forests carry very different coefficient sets. See below for the thresholds.
utils/precomputed_esvd_coefficients.py:807 · _determine_forest_type()
07
Twenty-two services are valued individually
For each ecosystem type, all 22 TEEB services are computed one at a time and summed into four categories. Every multiplier is applied at the individual service level, never to the category total.
utils/precomputed_esvd_coefficients.py:980–1008
08
Types are summed to an area total
Per-type totals are accumulated into the area's annual value, with per-type results retained for the composition breakdown and the PDF report.
app.py:5705–5706

The core formula

Everything in stage 07 reduces to one line, evaluated once per service per ecosystem type.

value = coefficient × area_ha × regional_factor × urban_mult × intactness
coefficient — the ESVD median for this ecosystem type and service, in Int$/ha/yr.
area_ha — this type's share of the drawn area, from stage 05.
regional_factor — GDP-based income adjustment (below).
urban_mult — applied only when the type is Urban; otherwise 1.0.
intactness — ecological condition, 0–1 (below).

The four TEEB categories are not weighted or rescaled — they are simply the sums of their member services.

CategoryServicesTEEB numbers
Provisioning61–6
Regulating97–15
Cultural518–22
Supporting216–17

Coefficients are pre-computed medians drawn from peer-reviewed studies in the ESVD/TEEB database, held as a literal table keyed by ecosystem type. Ecosystem names normalise to that keyspace by lowercasing and replacing spaces with underscores, so Rivers and Lakes resolves to rivers_and_lakes.

Regional adjustment

Coefficients are global medians, so they are adjusted toward the local economy using an income-elasticity method. The country is derived from the point's coordinates.

factor = 1 + ε × ( country_GDP / global_GDP − 1 )
factor = clamp( factor, 0.4, 2.5 ), rounded to 2 dp
ε (income elasticity) defaults to 0.6. Global GDP per capita baseline is 13,673 (World Bank 2024). The bounds prevent extreme values in very rich or very poor economies; the rounding matches what is displayed to the user.

A factor above 1.0 means the local economy is wealthier than the global average and services are valued upward; below 1.0, downward. With ε at 0.6 the adjustment is deliberately sub-proportional — a country at twice the global GDP gets a 1.6× factor, not 2×.

Verified deviation

Marine is hard-coded to a regional factor of exactly 1.0, on the reasoning that open ocean is international waters with no meaningful host economy. This overrides any coordinate-derived factor and any explicit override passed in. Rivers and Lakes and Coastal are not exempt — they receive normal adjustment. So reclassifying the same water points from Coastal to Ocean changes the result by both the coefficient set and the presence of the regional factor.

Ecological intactness

Intactness scales value by ecological condition — a degraded forest delivers less than an intact one. Three sources feed it, in precedence order.

SourceGranularityBehaviour
Indicator-driven Per service On-the-ground indicator scores compute a distinct multiplier for each of the 22 services. Used when the feature is enabled and the ecosystem resolves to a wired project type.
EEI (satellite) Per ecosystem Ecosystem Ecological Integrity fetched per sample point from Earth Engine, averaged per ecosystem type, converted from 0–1 to a percentage.
Manual sliders Per ecosystem The user's own percentage per ecosystem type, used when EEI is switched off.

When a dict of per-service multipliers is supplied, any service missing from it defaults to 1.0. When a single scalar is supplied instead, it applies uniformly to all 22 services.

Not every EEI response is a measurement

When Earth Engine fails to initialise, the EEI service does not return an error. It returns latitude-based estimates and marks them "demo_mode": true. These are fabricated, but they look entirely plausible — in range, varying smoothly with position — so nothing downstream would notice them on inspection. EVE therefore treats the flag, not the shape of the value, as the signal.

ResponseSignalTreatment
Real measurement source present Used — averaged per ecosystem type.
Real, but no data nulls + message Used as real. Ocean or a dataset gap legitimately has no pixel; this is not fabrication.
Fabricated demo_mode: true Discarded before it can reach a valuation.

The flag is checked twice. A top-level demo_mode means Earth Engine never came up and every result in the batch is fabricated; a per-result flag means Earth Engine is up but that individual coordinate fell back. A false top-level flag does not permit skipping the per-result check.

An ecosystem whose EEI came back entirely demo does not fall through to an optimistic 100% — it takes a deliberately conservative 50%. An ecosystem with even one real point uses that demo-free average instead. The API's own averages block is deliberately unused, because it blends fabricated and real points into a single number that cannot be separated afterwards.

None of this is silent. When any point returns demo data the user is told how many points were affected and which ecosystems fell back to 50% — both in Summary Statistics and in the exported PDF.

Assumption, not verified

All of the above is EVE's client-side handling. The EEI service itself lives in a separate repository, so the contract it relies on — that the service sets demo_mode on every fabricated result and never on a real one — has not been checked against the server. If that holds in only one direction, this logic misclassifies silently.

Lookup falls back rather than failing

Resolving a type's intactness tries an exact key, then a title-cased key, then — for forests — generic Forest, then Temperate, Boreal, Tropical in turn. If nothing matches it returns 1.0, meaning full intactness. A naming mismatch therefore produces a silently optimistic result rather than an error.

Forest subtype thresholds

Applied only when the routed type is generic Forest and coordinates are available. Evaluated on absolute latitude, so the rules are hemisphere-symmetric.

ConditionResolves to
threshold ≤ |lat| ≤ 70Boreal forest
|lat| ≤ 25Tropical forest
30 ≤ |lat| ≤ 45Temperate forest
25 < |lat| < thresholdTemperate forest
no matchTemperate forest

The boreal threshold is 60° inside the European Atlantic zone and 50° everywhere else, reflecting the Gulf Stream pushing boreal conditions further north in western Europe. The Mediterranean band carries named sub-regions — Mediterranean Basin, California, central Chile, Western Cape, southwestern Australia — but all five currently resolve to temperate forest, as does the band's fallback.

Behaviour worth knowing

Rounding is intentional

Composition shares are rounded to one decimal place before area is computed. This is deliberate: it keeps the arithmetic consistent with the percentages displayed in the UI, at the cost of the per-type areas not summing exactly to the drawn area. Preserve it when editing the calculation path.

One land-cover multiplier, applied to every type

After per-type valuation, an optional per-ESA-code multiplier is applied to that type's total. The code it looks up is taken from a single landcover_class on the detected-ecosystem record — not from the type being valued in that iteration. In a mixed-composition area this applies one code's multiplier to every ecosystem type. Flagged as observed behaviour; I have not established whether it is intended.

No NDWI water masking runs

NDWI code exists in two modules but neither executes. utils/natural_capital_metrics.py is never imported anywhere. The NDWI logic in utils/satellite_data.py is reachable only through ecosystem_services.get_ecosystem_service_values(), which app.py imports at line 1343 and never calls. Any document describing open water as masked out is describing an earlier design.
